# iOS 原生体验与工程质量标准

日期：2026-09-26。适用于全部开发阶段，与[产品设计](../IOS_DESIGN.md)、[构建说明](BUILD.md)共同执行；实际完成情况记入[开发记录](DEVELOPMENT.md)。本文中的性能数值、采样方法和实施顺序是项目设计默认，尚无达标实测，不是 Apple 的性能承诺。

## 1. 产品要求

**本 App 以用户当前 iOS 27 真机为主要体验目标，采用最新稳定、适合本项目的 Apple 原生技术。视觉品质、启动速度、小组件、动画连续性、触控响应以及内存与能耗，必须共同参与技术选型、架构设计、开发和验收。功能可用只是基础门槛；核心体验未达标时，不能宣布该功能完成。**

“极致体验”具体指：信息清楚而精致、打开即可开始操作、输入即时呈现、滚动和转场连续跟手、状态和反馈可信、小组件实用且与主 App 一致、长时间使用仍稳定。以 Apple 系统应用的交互一致性与响应品质作为体验参照，保留本项目已经确认的中性卡片与记账布局。

优化必须守住精确金额、事务、防重、草稿和恢复规则。性能改进不能通过提前显示保存成功、丢弃输入、跳过校验或展示错误余额换取。所有模块从第一版可操作页面起执行本标准，P6 负责整合打磨与完整验收。

## 2. 最新稳定技术与版本管理

2026-09-26 核查：Apple 已发布 iOS 27.0，官方兼容表列出稳定 Xcode 27、iOS 27 SDK、Swift 6.4 编译器及 Swift 6 语言模式。因此本项目下一步工具链升级目标为这组稳定版本；实施时再次核对最新稳定补丁、具体 build 与可用环境，不以测试版为默认。[iOS 27 发布记录](https://developer.apple.com/news/releases/?id=09142026a)、[Apple Xcode 兼容表](https://developer.apple.com/xcode/system-requirements/)

| 管理项 | 项目规则 |

| 最低部署系统 | 当前工程为 iOS 26.0，和主要体验目标 iOS 27 分开管理。新 API 做可用性处理；旧系统兼容不能削弱 iOS 27 的主要体验。若保留兼容明显增加成本或妨碍目标，提出提高最低版本的具体迁移方案并同步所有配置 |

SwiftUI、Observation、Swift Concurrency 是界面与状态实现的首选；导航、表单、键盘、菜单、面板和符号优先用系统组件。局部 SwiftUI 确有能力或性能限制时，可封装 UIKit／Core Animation，并提供测量与维护理由。当前范围不引入跨平台 UI 框架或用网页承载核心记账界面；Swift Charts、WidgetKit、App Intents 等按实际功能需要采用。

工具升级必须核对构建宿主要求，更新 `config/toolchain.json`、`project.yml`、适用的 `Package.swift`／依赖锁、构建脚本与文档，执行包测试、App／UI 回归、arm64 Release 构建及同一 App 身份覆盖安装。模拟器运行时单独记录，保留最低支持系统的兼容性回归。完成后才把“目标版本”改为“已验证基线”。

CI 暂无目标 Xcode 时，登记缺失项、可行的兼容 macOS 环境或官方工具安装路径、下一次验证动作；旧链路仅作过渡。不能为了 runner 现成可用而长期停留在旧 SDK，也不把配置写成新版本当作升级成功。使用固定路径与版本校验，禁止未验证的 `latest` 漂移。

## 3. 界面品质、动画与操作手感

### 3.1 视觉与系统融合

- 沿用产品设计第 5 章的中性卡片、较轻字重、等宽金额、共同中轴、彩色分类图标；统一颜色、字体、间距、圆角和状态组件。长金额、负号和币种完整可读，空状态、错误、加载和成功状态都需完成设计。
- 使用最新稳定 SDK 的系统控件与恰当的系统材质。Liquid Glass 用于适合的导航与操作层；财务内容保持稳定、清楚的背景，不将整页卡片玻璃化，也不叠加大量模糊、阴影或透明层。系统控件的尺寸与间距优先遵循系统，业务卡片的具体初值按产品设计执行。[Apple Liquid Glass 适配说明](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)
- 页面首次呈现、数据到达、键盘出现、底部安全区变化和主题切换时避免闪白、布局跳动和焦点丢失。确需加载时保留稳定布局；已知旧数据标明时间，未知金额不能用 0 填充。
- 中文／英文、浅色／深色、最大辅助功能字号、VoiceOver、增强对比度、减少透明度、减少动态效果随页面同步检查。触控区域至少 44×44 pt，语义标签和焦点顺序可理解；降低动效时仍给出明确结果反馈。

### 3.2 动态交互

- 返回、拖动面板、滚动、切换页签及键盘交互遵循系统行为。交互转场随手指连续变化，允许中断、反向与取消；快速重复操作不排队播放过期动画，不吞点击，不丢草稿，不误触底层页面。
- 区分“按下反馈”“正在处理”“已保存”。按下立即响应，成功提示及成功触觉仅在事务提交后出现；等待期间防止重复提交，失败保留输入。键盘输入与金额计算器不能等待数据库写入才更新屏幕。
- 优先系统转场与弹簧动画，统一同类动作的节奏。自定义非交互微动效初值为 120—200 ms，面板／状态转场约 200—350 ms；这是调校起点，不强改系统动画时长，也不把动画时长当响应时间。动画未结束仍允许合理的下一步操作，不用固定延时等待动画后才启动工作。
- 金额变化只做有意义的轻量过渡，财务真实值与读屏值始终明确，不让数字持续滚动或用动画中间值参与计算。滑动浏览、普通输入不反复震动，触觉仅用于关键选择、确认或错误，尊重系统设置。
- 正常温度、未开低电量模式且系统允许时，在支持 ProMotion 的设备上充分利用高刷新率；在 60 Hz 及系统动态调整刷新率时仍保持正确节奏。自绘内容依据时间与显示节奏推进，不靠高频 Timer，也不通过空转强迫持续 120 Hz。[Apple ProMotion 指南](https://developer.apple.com/documentation/quartzcore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays)

## 4. 性能预算与测量口径

以下为首次工程验收门槛，覆盖空账本、1 万笔与 10 万笔合成账本；达到门槛后继续依据体验和剖析结果改善，不以“刚好达标”终止已确认问题的修复。计时使用统一时钟，记录 p50、p95 与最大值；p95 指 95% 样本不超过该值。

| ID | 场景与计时边界 | 设计门槛 |
|---|---|---|
| Q01 | 进程不存在的普通冷启动：性能工具记录的系统启动起点 → 首页必要本地数据就绪且可操作记账入口 | p95 ≤ 1,000 ms；首帧另计，不能用启动图或空壳提前结束计时 |
| Q02 | 进程仍驻留的回前台：系统激活场景 → 可继续原操作 | p95 ≤ 300 ms；失去进程后按 Q01 计，不混入暖启动 |
| Q03 | 点击、按键／计算器输入、切换选中项：工具记录的原始输入事件时间戳 → 第一处可见反馈 | p95 ≤ 100 ms，争取 ≤ 50 ms；包含主线程排队时间，不代表业务已提交成功 |
| Q04 | 点击＋的原始事件时间戳 → 面板接受首个实际输入；键盘首次可用单列测量 | 面板 p95 ≤ 200 ms，含键盘的完整输入就绪 p95 ≤ 300 ms；以实际接受输入为准，不等待系统转场完全结束 |
| Q05 | 普通记一笔：点击保存 → 本地事务持久化完成且相关可见金额更新 | p95 ≤ 200 ms；失败、重复点击、连续记账同测，不能通过延后真正落盘伪造成功 |
| Q06 | 10 万笔流水的首屏／筛选／翻页：提交查询 → 首批结果；另计到实际显示 | 查询 p95 ≤ 300 ms，可操作结果 p95 ≤ 500 ms；增量加载不重置滚动位置。输入防抖等待计入用户端到端时间 |
| Q07 | 常用月度汇总与分析：操作 → 正确结果显示 | p95 ≤ 1,000 ms；复杂全量重算单列，不占用主线程，提供真实进度与取消边界 |
| Q08 | 连续滚动、面板拖动、导航与键盘转场 | 每段至少 30 s、至少 3 段；每段 hitch time ratio ≤ 5 ms/s，且无可重复的 ≥ 100 ms 停顿。按实际显示节奏分析，不以平均 FPS 掩盖卡顿 |
| Q09 | 1 万行导入、备份、全量重算 | 主界面持续响应；有可感知进度时至少每 250 ms 发布一次有界更新，取消请求 ≤ 1 s 被确认；是否允许立即停止依事务边界说明，已提交部分不能误报为取消回滚 |

120 Hz 的单帧时间约 8.3 ms，60 Hz 约 16.7 ms，CPU、布局、渲染与系统工作共享这段时间。连续交互中，项目自身主线程工作以每次更新约 5 ms 以内为工程预算；需结合渲染与实际 hitch 共同判断，不能以某个函数小于一帧就宣称无卡顿。Apple 的响应性说明为预算依据，上表具体门槛为本项目制定。[Apple 响应性指南](https://developer.apple.com/documentation/xcode/improving-app-responsiveness)

首次安装、升级迁移、恢复后重建、首次唤起键盘和缓存未命中独立分组测量，保存全部样本与最慢原因，不能删除这些样本美化普通路径。迁移与重建须在实现前按源版本、数据规模和工作量记录专项耗时预算，不能套用普通启动的 1 秒限制，也不能没有预算地无限等待；反馈与长任务响应仍按 Q03、Q09 验证。关键迁移未完成时明确阻止不安全写入，展示真实状态，不以快开为由展示半本账。

Q01 须覆盖进程初始化之前的系统启动阶段，不能只从 App 的 `init` 或 `.task` 开始计时。启动工具的标准首帧指标与额外的“首页可用”标记分别记录并关联到同一次启动；无法取得完整起点时标为待测，不用局部耗时代替。用户点图标到可操作的端到端录屏可另作体验证据，不与工具数据混算。普通进程冷启动不等同设备重启后的磁盘冷缓存，后者另列首开组。

Q03—Q07 的端到端操作计时不得从按钮处理闭包已经开始执行后才起算，也不能把仅设置了 SwiftUI 状态当成内容已显示；需要工具事件与呈现证据。应用内 signpost 用于分段定位，时间戳须校准到同一时钟。无法观测起点、真实呈现或首个输入时标注测量边界，不能直接填为端到端达标。

### 4.1 测试条件与证据

- 主验收使用 iPhone 16 Pro Max／iOS 27 的 Release 构建，记录设备与 OS build、App commit／包哈希、Xcode／SDK／Swift、数据规模、缓存状态、电量、低电量开关、温度状态及是否连接调试器。计时验收避免调试器干扰；剖析单独记录工具开销。
- 普通冷启动与回前台各至少 30 次；普通响应、保存、查询和分析按场景与数据规模各至少 100 次，冷缓存与热缓存不混算。系统首次路径及迁移按可复现设置分别至少 10 次；大任务至少 3 次。使用统一合成种子，含跨年记录、多账户、长名称与不同文字，不只测几条短记录。
- 持续滚动、开关记账面板、编辑与返回各循环至少 20 次；再执行至少 15 分钟混合记账／查询，记录内存峰值、静置后占用、CPU、能耗和热状态。缓存需有上限且预热后趋于稳定；持续内存增长、泄漏、内存终止或 App 导致的持续异常发热均不能通过。
- 同设备、系统、数据和步骤下与上个已通过版本比较；任一关键耗时或峰值内存／能耗指标退化超过 10% 时复测并解释，确认由本次改动导致则修复或记录经评审的取舍，不能以仍低于绝对门槛忽略。小数值的测量噪声需给原始样本；不以粗糙的电量百分比充当能耗证据。
- 分别检查正常模式、低电量模式、系统降低刷新率、减少动态效果、前后台切换以及飞行模式。受系统限制的场景单列结果和适配，不承诺恒定 120 FPS；不能把正常条件下的 App 瓶颈归咎于系统。

使用 Instruments 的 Time Profiler、SwiftUI、Animation Hitches、Allocations／Leaks 与可用的能耗工具定位问题；通过 signpost 标出启动、查询、提交与首屏可用边界。XCTest 的启动和 signpost 性能指标用于可重复回归，真机交互与帧时序确认最终手感。SwiftUI 的重复更新和耗时 `body` 应具体剖析。[Apple SwiftUI 性能指南](https://developer.apple.com/documentation/xcode/understanding-and-improving-swiftui-performance)

Windows 领域测试验证规则，云端模拟器验证编译与交互正确性，两者均不能代替真机速度、ProMotion、触觉与能耗测试。当前 Windows＋云端流程尚无完整的连接真机 Instruments 测量证据；实施时须补齐可用的 Mac／真机剖析链路或同等可信的设备测量。没有测量条件的项保留“待测”，用户视频可作为问题证据，不能据此填写精确 p95 或耗电达标。

## 5. 架构必须为体验服务

| 路径 | 实施要求 |
|---|---|
| 启动 | 只在关键路径打开必要存储并取得首页最小数据和草稿；延后非必要模块初始化、全量扫描、导出、NAS 与网络请求。离线可打开、可记账，启动不等待云端 |
| 数据读写 | 单笔操作使用增量事务、索引查询和分页；不把全量载入、全表重写、全账本重新校验设为每次输入／保存／首屏的固定前提。迁移、恢复、导出仍保持完整一致性校验 |
| 首页与流水 | 只查询所需汇总和可见记录；最近 5 条不能每次对全库排序。复杂筛选、分组、报表在隔离的工作上下文完成，派生结果按账本版本缓存，不能混合新旧账务状态 |
| SwiftUI 状态 | Observation 按页面与实体限定依赖，列表 ID 稳定，保留滚动和焦点；单条变更不重建整本账的可见状态。`body` 不做磁盘 I/O、图片解码或全量计算；Lazy 容器不能代替数据库分页 |
| 并发 | MainActor 只承担轻量状态与 UI 更新；重计算、解析、哈希、压缩及存储 I/O 使用合适的 actor／执行器。`async`、`Task` 或 `actor` 字样本身不证明已离开主线程，必须核实隔离与实际调用栈 |
| 任务生命周期 | 搜索等过时读请求可取消并由版本拦截旧响应；限制并发、合并重复工作、避免输入每变一字就整库写入。草稿可合并持久化请求，但必须保持最新输入、退出恢复和提交同事务规则 |
| 资源 | 图标与图片按显示尺寸解码、异步加载、有界缓存、稳定占位；页面消失后停止无用任务。重计算、Widget 刷新和备份按变化合并，无意义轮询与持续装饰动画不得占用 CPU／GPU |

任何缓存、分页或增量方案仍以 SQLite 中同一套权威账务为准；保存、草稿清除／续写、版本检查与操作防重的事务关系保持不变。新快照要标注账本代次／版本，恢复后丢弃旧任务及旧缓存，不能通过后台更新覆盖恢复后的数据。

## 6. 桌面小组件品质

Widget 是完整产品体验的一部分。范围继续为快速记账、月消费／预算、可用资金／到期、投资和物品；不增加锁屏 Widget 或金额隐藏开关。扩展、App Groups 和免费重签安装链路仍须实际验证。

- 使用 WidgetKit＋SwiftUI，App Intents 用于适用的配置与入口。记账通过深链进入主 App 的预填草稿并由用户保存；处理已有草稿的冲突，不在扩展中绕过领域规则直接写账。
- 每种 Widget 明确支持的尺寸和内容密度，在所声明尺寸逐一验收；检查浅色、深色、系统着色／强调色、内容边距、长金额与长名称。正文与主 App 采用同一财务口径和视觉语言，系统着色后仍可区分正负与状态。
- 从 App Groups 中读取小而完整的只读快照，包含账本代次、版本、数据截至时间与完整性。主 App 事务成功后原子发布快照并请求刷新；发布失败保留最后一个完整快照、标明时间并可重试。数据库提交和快照文件发布之间的中断需要恢复机制，不声称二者天然处于同一事务。
- 明确首次无数据、尚未配置、陈旧、缺估值、读取失败和恢复后的表现，不展示虚构金额，不把旧投资收益写成今日。恢复切换后旧代快照不得混入新账本。
- 分别记录“数据提交”“快照发布”“刷新请求”“系统实际显示”。WidgetKit 的 timeline 与刷新由系统调度，更新请求不等于立即刷新；预先安排已知日期变化，不用高频轮询维持假实时。[Apple Widget 更新机制](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date)
- 从主 App 未启动、后台和前台三种状态验证点击跳转、预填、返回与再次点击；无目标账户／记录时给出明确可恢复入口。扩展内存、执行时间与后台能耗单独检查，禁止载入整本账用于一张小组件。

## 7. 每批交付的完成标准

每个新增或修改页面都必须同时提交功能结果、视觉／无障碍检查、关键交互录屏和对应性能记录。记录至少包含：场景 ID、构建与设备、数据规模、测量方法／样本数、p50／p95／最大值、对比版本、证据路径、状态、未达标原因与修复动作。状态仅用“待实现／已实现待测／通过／未通过／受系统或环境限制”；外部资料和代码存在不能填写为通过。

核心链路出现可复现卡顿、输入丢失、错误成功反馈、明显布局缺陷、数据不一致或未满足预算时，先修复再宣布该模块完成。临时内部测试包可以提供，但必须列出未通过项。性能门槛修改要记录依据和影响，不通过放宽数值、缩小数据集或删掉失败样本消除问题。

稳定大版本升级和影响热路径的改动都需要前后对照；普通文案等低影响变动只验证受影响页面，不重复执行无关的全套性能采样。业务测试通过、截图看起来正常与体验验收分别记录。

## 8. 当前差距与实施优先级

截至本次文档修订，已存在 SwiftUI、Observation、Repository actor 和基本数据一致性设计；尚无本标准的性能达标证据。当前存储仍整本读写，首页存在全量排序／派生计算，流水仍在内存筛选分组，Widget target 与共享快照尚未建立。这些是已知实现差距，不能由“使用 SwiftUI”抵消。

1. 将稳定 Xcode 27／iOS 27 SDK 升级验证列为近期工程任务；建立 Q01—Q09 的测量边界，保留现有构建作为对照。
2. 优先治理启动、首页、记账、保存和流水的热路径：增量事务、最小查询、索引／分页、细粒度状态与有界缓存；同步回归备份、防重和数据恢复。
3. 在这些高频页面落实最终文字与布局、键盘与面板交互、连续转场和必要触觉，取得真机证据；继续扩充业务模块时复用已验收组件。
4. 尽早完成一个真实 Widget 的免费签名、共享、刷新与冷启动跳转验证，再扩展其余类型；不等到最后才发现安装链路问题。
5. P2—P5 每阶段执行相同体验标准，P6 集中进行全量、多语言、多状态与长时间使用验收。当前文档更新不代表工具链已升级或上述优化已实现。
